## 2. Proposed minimal period model

One tenant control record, collection `Acc_PeriodControl`, with distributorId, firmId, policyVersion, configurationState (CONFIGURED only after explicit onboarding), coverageStart, coverageEnd, revision, and embedded periods. Unique index on distributorId + firmId. Each period has immutable id, financialYear label, startDate, endDate inclusive, OPEN/CLOSED status, revision, last transition actor/time/reason/audit identifier. Dates are validated ISO civil dates in IST. Propose fixed calendar months within the existing April 1–March 31 year; no alternate fiscal calendar silently introduced. Financial-year bounds are derived and checked against each period; no separate year-close flag that could conflict with monthly state. A year is closed only when all twelve configured periods are closed.

Periods must exactly cover declared coverage, with no overlaps, gaps, duplicate IDs or cross-year months. New years are explicitly configured, never automatically opened. Control document size must be bounded; a later change to storage partitioning is a separate design decision. A unique tenant record plus one atomic revision check serializes boundary configuration, avoiding reliance on an overlap query or unique start-date index alone.

Missing tenant record, missing coverage, malformed configuration or missing period returns PERIOD_CONFIGURATION_REQUIRED and blocks affected financial writes. It does not assert that historical periods were open or closed. Reads remain available and show configuration status through API metadata where relevant. Proposed adoption: inventory and reconcile separately, obtain a tenant-specific signed coverage/status schedule, then create that schedule with audit atomically. No automatic historical inference, blanket-open seed or blanket-close migration. Until that policy and schedule are approved, enforcement cannot be safely enabled for older tenants. Operational rollout must explicitly account for the resulting write block; no environment-variable bypass is proposed.

## 3. Authorization, audit and concurrency

Proposed permission operations in the existing engine: FINANCIAL_PERIOD_VIEW/view, FINANCIAL_PERIOD_CONFIGURE/add, FINANCIAL_PERIOD_CLOSE/edit, FINANCIAL_PERIOD_REOPEN/edit, FINANCIAL_ADJUSTMENT/add. Add them under an explicit accounting module/group, with normal-user defaults false. Keep existing document add/edit/delete permission requirements as well. Proposed initial authority is DISTRIBUTOR_ADMIN via the current known-operation admin rule; delegated grants require explicit assignment by that administrator. ACCOUNTANT or MANAGER role alone grants nothing. Approval of this authority model is required before implementation. No permission permits posting directly into a closed period.

Close/reopen/configure requires authenticated tenant, expected revision, nonempty reason, request/idempotency key, and server-side authorization. Reopen is an explicit recorded transition, not an implicit override. Reopening does not rewrite history or automatically authorize statutory amendments. Reject stale revisions and conflicting idempotency-key payloads; repeat identical requests returns the recorded outcome. Configuration boundaries cannot be changed once referenced by an event; extend coverage by adding periods.

Use writeAuditEvent in the same transaction as the control transition. Store before/after period state, actor identity (including stable principal id), reason, revision, policy version, request ID, and transition id. Failed audit means rollback. No audit update/delete endpoint. Durable audit retention and privileged database access controls need operational approval, not a claim of tamper-proof logging from this schema alone.

Every financial write transaction must actually update the same control record (conditional revision plus increment) after checking affected periods. Close/reopen uses that same write conflict point. A snapshot read alone is insufficient: a posting must not commit based on stale OPEN state while closure commits concurrently. Retry the complete transaction and revalidate; deterministic lock order if multiple control records ever become necessary. Close verifies defined reconciliation gates, unresolved adjustments/imports and in-flight work using the same serialization protocol. External GST operations cannot be made atomic by a Mongo transaction; handle explicit pending/failed state without treating them as a completed cancellation.

## 4. Central date contract

Propose `validateFinancialOperation(context, session)` in financialPeriods.js, using authenticated scope, operation kind, source snapshot/version, original document date, latest posting date, requested adjustmentDate, replacement document date and affected opening/allocation references. All required dates must be valid civil dates. Future effective dates are rejected in the initial policy; future-dated instruments remain distinct from accounting effective dates. This restriction is proposed for approval.

For create: effective date normally equals document date; require configured OPEN target. For edit/cancel: require explicit actual approved adjustmentDate (no client voucher-date fallback); require adjustmentDate >= latest posting effective date and original document date. Validate replacement document date separately. An ordinary in-place edit/cancel requires original and all affected posting/replacement periods OPEN. A later replacement financial event uses adjustmentDate; source document date remains separately preserved in the revision snapshot. All permission, date and period checks run before document, stock, numbering or allocation mutation, and again in the shared posting boundary under the same session/control write.

Closed-source edit/cancel is rejected by ordinary routes. Explicit authorized adjustment creates a separate immutable adjustment document linked to source ID/version and affected journal IDs; original header/items, journal amounts/dates and past allocations are preserved. Its accounting date is the approved current open-period date. It may post a linked opposite and replacement pair where appropriate; a delta-only adjustment requires explicit amounts/reconciliation, not another reversal of the same original. Original closed event status is preserved; reversal/adjustment linkage determines remaining correction eligibility. Unique operation keys and remaining-adjustable-amount checks prevent duplicate corrections. The existing reverseSourceJournal must not be reused blindly for this path because it changes original status and assumes the latest source event is reversible.

Adjustment documents store tenant, original reference/date, effective date, approval actor/time, reason, immutable financial snapshot, stock/allocation consequences, idempotency key and journal links. Use a new source type FINANCIAL_ADJUSTMENT and a separate source ID; never disguise an adjustment as changing the original bill date. No generic journal entry alone authorizes stock/GST changes. For a financial-only adjustment, explicitly record no inventory effect. For quantity/return changes, use an approved linked current-date stock/return workflow or reject; do not alter original stock history.

Posting service requires a validated operation context and active session, checks the effective date and tenant itself, and obtains/checks the serialization guard. A caller cannot supply a trusted `validated: true` flag. Direct Journal.create/update/bulk writes must be enumerated and restricted to the controlled service; legacy opening status updates must be removed from new-event paths. Existing idempotent no-op reversals must still create no extra event; retries returning a committed result require no new posting. Preserve Phase 2A latest-event selection and report arithmetic.

## 6. Opening compatibility without rewriting history

Keep absent opening-ledger marker = legacy supersession semantics. Existing OPENING_BALANCE journals continue POSTED-only selection, exactly as Phase 2A; including all legacy REVERSED rows would double count superseded amounts. Do not backfill markers or manufacture missing historical opposites.

New event-ledger opening roots use explicit ledgerModel=EVENT_V1, an immutable logical opening identity and event version. Report predicate becomes transaction events as today, legacy openings POSTED only, EVENT_V1 openings both POSTED and REVERSED (with dates and reversal links). Add this optional marker with no default to Journal: a schema default could accidentally classify existing records. Distinguish report-generated opening carry-forward rows from persisted opening source events; source strings alone must not decide provenance.

An untouched legacy opening remains legacy. A correction to it requires explicit per-root conversion approved at A: retain the legacy active journal/status, append an EVENT_V1 opposite linked to its exact ID and a replacement at A. The legacy active contribution plus event correction pair yields the replacement after A and preserves the pre-A balance. Removed legacy amount gets an opposite only. Mark the logical root as having entered event mode in separate versioned metadata, without changing original journal dates/status; future edits reverse only the latest event-mode replacement, never the legacy row again. Atomic unique operation/root version prevents double bridging. Previously superseded legacy rows remain excluded. This preserves the existing baseline but cannot reconstruct history already lost through legacy supersession.

For newly created openings, every edit/removal emits real opposite/replacement events at A; no bulk status supersession. Preserve row.date as reference date and postingDate as initial recognition date; revision/current outstanding fields are projections, not financial history. EXISTING references never add an opening journal; mode changes need an explicit correction operation, not an implicit save. openingBal remains a summary, never another posting.

Allocated legacy rows retain current protections. New allocation/release operations use tenant-scoped immutable allocation events at parent A with root and voucher links; mutable allocatedAmount is only the current projection. This is necessary to preserve as-of outstanding history, which the current counter alone cannot prove. Settling an old invoice is allowed as a new current-period event without rewriting its historical amount; closed-source corrections must not decrement old persisted allocation snapshots. Distinguish settlement projection updates from document financial edits. Old allocations without events remain an explicitly limited baseline; no invented historic timeline. Reconciliation and selected-root enrollment are separately approved, never automatic mass migration.

## 7. Required schemas (proposal only)

1. New Acc_PeriodControl as section 2; no period flags on Mas_Company or duplicate calendar on GeneralSetup.
2. New T_FinancialAdjustment: fields in section 4; unique tenant/idempotency key and tenant/source/version/operation identity; immutable approved payload, approval audit link and posting status.
3. Acc_Journal optional ledgerModel, operationId, adjustmentId, sourceDocumentDate, sourceRevision and period/policy revision metadata. Keep documentDate as effective accounting date for compatibility. Retain reversalOf and unique source/version index; additions must not reinterpret existing rows.
4. New T_OpeningEvent/AllocationEvent immutable tenant/root/version records for new opening corrections and allocation history; unique tenant/root/event version and operation key. OpeningTransaction gains optional event-mode root/current revision reference, leaving legacy absent. Final model may share a single typed event collection, but its event types and unique identities must be explicit before coding.
5. Existing document schemas need immutable revision snapshots and adjustment links/metadata where absent, including original header/items/tax/stock/allocation state. Server inline schemas and transaction/p0 voucher schemas must be changed alongside their handlers; storing only the newest header is insufficient. Existing receipt reversal audit currently captures before after marking REVERSED; capture true before snapshot.
6. Reuse Sys_AuditEvent schema; no new audit store required. Add stable actor/approval IDs inside before/after if keeping its schema unchanged. Reuse Mas_SecuritySetup Mixed map with explicit catalog operations; no parallel role table.

## 8. Historical risks and limits

Unknown period configuration, document/journal date mismatches, malformed dates, missing journals, repeated reversal chains, missing actual unique index, imported document-number collisions and standalone openingBal records need separately authorized read-only assessment. Changed Phase 2A reporting can expose existing chain arithmetic. Legacy opening supersession and allocation counters cannot establish past as-of history. Some operational/GST reports use mutable documents rather than journal events; immutable revision-aware selection is needed for any report claimed historically correct. No automatic historical repair, reverse-all migration or inferred period status is safe.

Current tests do not prove real database rollback, close/post concurrency, historical production integrity, authenticated flows or statutory compliance. Trial balance cutoff semantics and remaining Phase 1 defects remain open; do not silently fix them under this design or claim full reconciliation. No performance claim is made for control serialization or new predicates.
